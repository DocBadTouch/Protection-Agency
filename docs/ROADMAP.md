# Roadmap

The current repository is a working alpha. The numbered items below are planned work, not a current feature or a promised delivery date.

`0.3.0a1` adds shared agent selection/capability reporting, a Codex-specific strict shell adapter, Codex configuration-control findings, and a native local-NTFS backend with Windows CI. CLI/MCP scanning remains shared. Protocol/platform tests do not establish real vendor-client enforcement. Codex native review/failure limitations and Windows filesystem restrictions remain explicit in [the matrix](AGENTS-AND-PLATFORMS.md). Next validation must cover both clients on actual supported user environments, including retail Windows, and measure whether strict Codex denials are usable.

The `0.2.0a1` milestone implements basic inventory consistency, exact proposed-release checks, selected startup execution-surface review, documentation context, and offline diagnostics. `0.2.0a2` adds a user-invoked pre-launch gate with complete-check requirements, limited terminal review, scoped content/identity rechecks, Git startup inspection, and marker/terminal integration tests. `0.2.0a3` adds explicit user-hook setup/removal with private backups, configuration checks, a trusted protocol probe, and project hook-disable detection. A diagnostic pass still does not verify a real client's loading or enforcement. Next enforcement work includes vendor-client end-to-end tests, verified client configuration boundaries, and runtime isolation or immutable snapshots.

`0.2.0a4` adds a first-time terminal workflow (`demo` → guided `setup` → guarded `open`), readable `check` results, plain diagnostics, and newcomer documentation. Terminal/marker tests exercise consent and gate behavior, not real native enforcement. The next usability validation is to observe 3–5 unfamiliar developers complete setup, explain a warning, and remove hooks without coaching. Five minutes is a design target, not a measured claim. Record routine-workflow review frequency before changing prompt policy; do not silence it through automatic execution approvals.

1. **Validate real clients and harden each platform boundary.** Exercise Codex and Claude profiles, native trust, event delivery, alternate tool paths, failure/timeout policy, disabled controls, and the before-start gate on Linux/macOS/native Windows. Record exact client/OS versions and inert markers. Review the native Windows ctypes/ACL/handle implementation independently, fuzz malformed input, verify MCP clients, and measure legitimate-project false positives and review frequency. Current [validation](VALIDATION.md) distinguishes native platform tests from unverified client sessions.
2. **Authenticated data-only intelligence updates.** Publish small declarative rule bundles, never arbitrary Python or shell plugins. Use an established signed metadata system such as TUF, pinned trust roots, threshold signatures, expiration, version/rollback protections, strict size/schema validation, atomic activation, and last-known-good state. Surface stale/expired intelligence in every relevant verdict. Client updaters may use a maintained dependency: do not hand-roll cryptography to preserve a zero-dependency marketing claim. Distribute executable upgrades separately with reviewed releases and provenance.
3. **Less intrusive execution review.** Build an execution broker that binds approval to a command, workspace snapshot, and dependency state. Isolate actual execution at the OS/container layer. Avoid reusing a clean verdict merely because a lockfile is unchanged.
4. **Broader dependency support.** pnpm/Yarn/Bun, richer Python requirements and PEP 751, manifest-to-lock consistency, installed artifact hashing, provenance attestations, direct/transitive attribution, and fixed-version guidance.
5. **Optional deeper analyzers.** Explicitly configured, pinned adapters for established SCA/SAST/secret scanners. Run them in isolation and normalize bounded findings. Never download and execute an arbitrary scanner suggested by the target repository.
6. **Community releases.** Publish versioned artifacts and checksums, release notes, maintainer/review practices, a contribution policy for sourced indicators, and reproducible benchmarks. Add GitHub CI/SARIF output once result schemas stabilize.

An LLM review tier may be useful for difficult findings, but it should be optional, visibly metered, and isolated from enforcement policy. No LLM judge or paid service is needed for the current scanner.
