# Threat model and limits

Protection Agency helps a developer inspect an untrusted project before an agent installs, imports, builds, or tests it. It also surfaces known dependency advisories that could affect shipped software. It is an alpha screening tool, not endpoint protection, a semantic auditor, or a complete software supply-chain security platform.

## Trust assumptions

The host, Python interpreter, scanner checkout, and user-level agent settings are trusted. The inspected repository, dependency metadata, package scripts, agent instructions, tool output, and remote advisory responses are untrusted. Keep the scanner and hook settings outside the inspected repository. A user with permission to modify the scanner or disable the hook can remove its protection.

No project package managers, build backends, Git hooks, imports, or tests are invoked by a scan. Symlink file reads and special files are refused. The scanner still parses attacker-controlled files inside the current Python process. File limits and bounded patterns reduce resource exposure; run it in a resource-limited process/container when inspecting hostile repositories. Traversal and network deadlines are cooperative, not a hard CPU or wall-clock kill.

## Coverage

Supported inventories do not prove they match an installed tree. Basic npm declaration/entry consistency and common stable-version constraints are checked, including represented transitive declarations and workspace records. This is a supported subset, not full package-manager resolution or synchronization validation. Full lockfile freshness, artifact integrity verification, provenance attestations, dependency reachability, environment selection, and SBOM generation are not implemented. The presence of an integrity field is checked, but its hash is not verified. All represented lock entries are considered, including development and environment-specific dependencies.

`requirements*.txt`/`.in` accept exact pins only, with simple extras, markers, and hashes. Includes, constraints, editable paths, ranges, direct URLs, and index directives are reported as gaps and not followed. Static PEP 621 declarations and simple dependency groups are checked against supported sibling Python locks. Stable numeric comparisons, npm full-version caret/tilde/comparators/disjunctions, and Python numeric comparators/compatible-release constraints are supported. Prerelease ordering, wildcard/partial npm selectors, environmental marker evaluation, direct-source resolution, and other syntax require review. Dynamic dependency metadata and Poetry-specific manifests require separate review. `uv.lock` and `poetry.lock` supply a wider inventory without resolving packages. npm lockfiles v1, pnpm, Yarn, Bun, PDM, Pipenv, and setup.py/setup.cfg dependency execution are unsupported and reported when encountered.

Proposed-dependency checks inspect an exact release identity, not the resolved graph or package bytes. The command adapter recognizes a limited set of simple install/invocation forms, with up to 32 extracted targets. It does not evaluate wrappers, expansions, requirements files, arbitrary command syntax, or every package-manager option. Those commands remain review cases. Online proposed-target queries additionally require explicit public registry provenance; unknown options and extra indexes suppress those queries. A bundled malicious identity is a published name/version match, not proof that bytes in a private registry are identical.

Quick scope does not inspect all application code. Standard scope includes quick-selected files and recognized project text; deep adds installed/generated directories under the same budgets. Selected execution surfaces include project agent hooks, MCP commands/URLs, editor folder-open tasks, `.pth` imports, Python startup modules, and native/Python build configuration. They are reviewed as configuration, not automatically classified as malware. Malformed or over-budget recognized configuration produces a gap. Ordinary Markdown/reStructuredText and selected README-like text files retain low-priority documentation indicators; agent instructions and configuration retain normal priority. Context is a filename-based heuristic, not proof that a file cannot execute.

Git metadata, cache directories, `.env*`, private-key extensions, arbitrary binaries, non-UTF8 data, and unknown extensions are outside source scope. Unicode tricks, computed imports, indirect execution, staged downloads, sophisticated obfuscation, prompt injection, business-logic vulnerabilities, zero days, and malware absent from available intelligence may evade detection.

## Privacy and intelligence

Offline scans make no network calls. Online scans send eligible public package names, versions, and ecosystems to the fixed OSV endpoint. They do not send source, absolute project paths, scripts, tokens, or lockfile contents. The service, proxy operator, and network infrastructure can observe those queries.

Source classification uses recorded inventory URLs and project `.npmrc` registry declarations. Unknown/private sources are omitted and reported. Plain requirements pins assume default PyPI in the absence of source directives. User/global package manager configuration, DNS policy, environment-specific index overrides, and registry credentials are not resolved. If a package name is confidential or its source uncertain, keep online mode off. This is not a promise that every private name can be inferred from arbitrary manifests.

The embedded IOC snapshot is small, version-specific, and dated. OSV coverage depends on upstream advisory ingestion; emerging attacks may not be listed. Failed requests, pagination limits, or skipped packages result in incomplete coverage. A zero-match result covers only the exact checked versions at the reported time. No background polling or incident alerting is implemented.

## Enforcement boundaries

MCP acts only when called and skills can be ignored/manipulated. Dedicated Codex/Claude adapters handle their shell tool, with configuration/protocol evidence separate from native enforcement. SessionStart adds context only. Claude requests native review for ordinary execution; Codex's strict adapter denies review cases because native `ask` is unsupported. Codex hook startup/timeouts may continue. These adapters never execute proposed commands or provide isolation; other tools need separate controls.

Startup-configuration findings do not stop lifecycle hooks that run before or alongside the SessionStart adapter. The separate `launch` command enforces a scoped preflight before it starts a caller-selected client. It cannot intercept client launches through another terminal/IDE or protect against code that already ran. `doctor` performs offline scanner self-checks plus optional user-hook configuration/protocol checks; native client enforcement remains explicitly unverified.

## Explicit user-hook setup boundary

The explicit `install-hooks`/`uninstall-hooks` commands and guided `setup` edit trusted user settings through the same editor. They require isolated Python and an external source installation. Reads/edits use pinned no-follow directory descriptors, bounded regular files, single-link and ownership/write-permission checks. Original bytes are retained in private backups before atomic replacement. Unrelated settings and later edits are preserved semantically, while JSON comments/formatting normalize. The reserved status message identifies owned handlers; it is not a signature or protection against someone who can already edit trusted user settings.

Advisory locks coordinate this tool's writers. Detected file/directory changes stop replacement, but another editor can ignore the lock and write during the final check/rename window. The filesystem is not frozen. Backups/locks remain local; backups can contain preexisting credentials and need the same care as the original file. ACLs, remote filesystem guarantees, compromised ancestors/host processes, and native-client reload behavior are not attested.

Diagnostics validate the canonical installed groups and reject marked modifications. A protocol probe reconstructs the current trusted guard command with `-I` and a sanitized child environment; it never runs arbitrary settings commands, a native client, project startup modules, or a package manager. The three test events exercise offline deny/read/error paths. This does not verify native settings precedence, event delivery, supported client fields, hook ordering, timeout/failure enforcement, or any sandbox. The required minimum client version is reported, not discovered or enforced by querying the client.

Project `disableAllHooks: true` is high-priority evidence that user hooks can be disabled. Setup and doctor conservatively inspect the selected root's `.claude/settings.json` and `.claude/settings.local.json`, without computing the full effective hierarchy. The scanner also flags recognized nested settings. Managed policy, CLI overrides, ancestor/additional-workspace settings, plugins, and other native configuration require separate review. These commands do not silently override explicit hook-disable settings or grant native permissions.

Agent-selected profiles honor known user environment directories or home defaults, with explicit settings overrides. Legacy explicit commands default to Claude; new guided setup asks for an agent and automatic opening requires selection. Global project-contained/relative config environment paths are rejected. Full native precedence/trust and CLI overrides are unverified. Codex hook-disable/managed-only controls in selected root/user TOML are read without editing and can prevent installation; recognized project controls produce `PA409`. Absolute paths can become stale after upgrades.

Guided setup requires terminal confirmation for a settings edit and binds it to the read file snapshot. Detected changes while prompting stop the edit; the editor's final noncooperating-writer race still remains. A post-install response-test failure leaves the edit in place for inspection; no blind rollback overwrites newer state. Printed shell hints use argument quoting and refuse control-character paths. No shell startup file is modified. The inert demo runs the trusted guard only, in a disposable empty directory, and does not certify a native client. `check` changes presentation, not scan policy. `open` searches a sanitized external PATH and delegates to the existing launch boundary; it never auto-approves review or installs hooks.

## User-invoked launch boundary

The scanner, Python runtime, chosen external client installation, caller-supplied client arguments, and trusted user/global configuration are part of the trusted computing base. `launch` requires Python `-I`, an external trusted scanner, and an absolute client executable outside the project. It does not authenticate the terminal operator, attest the chosen binary's provenance, or verify every library the client will load.

The launch gate stops on high-priority findings and incomplete coverage/advisories. A limited explicit terminal review can acknowledge lower-priority findings; piped answers, persistent receipts, and automatic yes flags are unsupported. Acknowledgment does not make a vulnerability or hook safe. A fresh local recheck compares selected file hashes, selected Git metadata/modes, root identity, and client file metadata before execution. The preflight expires after five minutes. Concurrent changes after the final check remain possible; this is not a filesystem snapshot or continuous monitor.

Launch additionally inventories a regular root `.git/config` and bounded non-sample hook files. Known helper settings and executable hook files are review surfaces. Config includes, indirect Git directories, shared/per-worktree configuration, custom hook paths, duplicate/unsupported Git syntax, and unreadable metadata remain gaps. No external helper/config target is followed automatically. This conservative subset does not implement all Git configuration semantics or inspect global Git configuration. Selected ancestor agent/editor settings outside the root produce gaps, while home/global client settings remain trusted.

Child startup sanitization removes known interpreter/shell/dynamic-loader and Git execution overrides, including exported Bash functions, and filters relative/project PATH entries. Git environment config pairs are bounded and known execution entries removed while other values are retained. Proxy/CA/auth settings are preserved without printing values. Relative or project-contained global-config environment paths are rejected. Sanitization cannot undo loader code that executed before the trusted Python launcher began, and it is not a complete environment or credential sandbox.

The launched client's arguments, additional workspace choices, global configuration, plugins, native filesystem tools, MCP servers, and post-launch execution retain the client's own behavior and permissions. Use OS/client isolation and minimal credentials. Startup-gate tests exercise an inert external client, marker files, and a pseudo-terminal, not a live vendor/model session.

Unsupported execution tools, alternative MCP servers, IDE extensions and autorun before the agent starts, shell startup files, another terminal, disabled hooks, client bugs, and approved commands remain outside this adapter. Project edits may race a check. User review does not make unknown code trustworthy. Use OS isolation, restricted network access, and minimal credentials for execution.

This project does not certify that a machine is uncompromised, recover stolen credentials, or make vulnerable software safe for end users. An already-compromised host can interfere with any local scanner. Prior malicious execution requires incident investigation outside this tool.

## Native Windows scope

The experimental backend is local fixed NTFS only. It uses held directory handles and handle-relative operations, bounded native enumeration, reparse refusal, and explicit ACL checks. UNC/network/removable volumes, alternate streams, reserved/path aliases, unsupported filesystems/ACL entries, and hard-linked settings are rejected. It does not fall back to ordinary settings writes. Foreign write grants are refused; current user, SYSTEM, and Administrators remain trusted owners/principals. OWNER RIGHTS entries are accepted only after owner validation. Backups/new settings use protected ACLs restricted to those principals.

Directory pins deny deletion, with write sharing permitted on the protected configuration parent for native rename. Read pins additionally prevent write opens. Native locks coordinate setup writers; snapshots recheck bytes/identity/ACLs before replacement. Same-user privileged processes remain trusted actors, and no immutable filesystem or post-check race immunity is claimed. Directory durability is not attested; post-replacement file-flush failure reports an applied warning. Native `.exe` startup rejects batch shims. Windows shell syntax remains conservatively reviewed; this is not a full PowerShell/cmd parser. See [the platform matrix](AGENTS-AND-PLATFORMS.md) and native CI evidence in [validation](VALIDATION.md).

The gate removes PowerShell module-path injection, resets Windows shell/system-directory variables from the native system-directory API, and disables current-directory executable lookup. Its POSIX shell must be an executable outside the project. This covers selected inherited startup variables, not all user/client configuration or extensions. The Codex relay uses a fixed system PowerShell with profiles disabled and literal trusted arguments.
